# v4.0 brief — structural reset

> Not iteration. Spec-to-code chain as spine, two workflows, ~50%+
> file reduction. Old 8-item brief becomes natural fallout.

## 1. Why v4.0

v3.x grew by accretion: 8 agents, 14 skills, 6 schemas, 22 dev-docs
(~8400 lines), lockfile-per-artifact plumbing, 6 language rule
subdirs. v4.0 reorganizes around the chain as the spine and cuts what
doesn't pull weight.

## 2. The chain

```
Business           Architecture        Component   Boundary
─────────────────  ─────────────────   ─────────   ────────────────────
PRD ──→ FRS ──→    SAD ──→ ADR ──→     TDD ──→     openapi.yaml
                                                        │
                                                        ▼
                                                       code
```

PRD and FRS are **separate files** (was: FRS embedded in PRD body).

| Layer | Artifact | Producer | Tier |
|---|---|---|---|
| Business | PRD-NNN.md, FRS-NNN.md | @product | T-B |
| Architecture | SAD.md, ADR-NNN.md | @architect | T-B |
| Component | TDD-NNN.md | @lead | T-B |
| Boundary | openapi.yaml (or asyncapi.yaml) | @lead | T-B |
| Implement | server-side code + unit tests | @backend | T-C |
| Implement | UI components / state / styles | @frontend | T-C |
| Verify (plan + tests) | TSR-NNN.md §test-plan + black-box test code (Stage 1, spec-bound) | @test | T-C |
| Verify (verdict) | TSR-NNN.md §verdict-evaluator (verdict, score table) | @evaluator | T-A |
| Verify (review) | TSR-NNN.md §verdict-reviewer (verdict, findings) + ADR review | @reviewer | T-A |
| Release | RELEASE-vX.Y.Z.md, RUNBOOK-vX.Y.Z.md, commits, TSR `S-SHIP-001` | `/orchestra ship` subcommand (folded from v3.x `@ship` agent — see §5c, decision §7.2) | n/a |

**Agent roster check.** v3.x ships 8 agents; v4.0 ships 8 (`@product`, `@architect`, `@lead`, `@backend`, `@frontend`, `@test`, `@evaluator`, `@reviewer`). Net-zero count masks two structural moves: `@architect` is split out of v3.x's `@lead` to separate Architecture (SAD/ADR) from Component+Boundary (TDD/openapi) — see decision §7.20; `@ship` is folded into the orchestra command surface, not deleted as a role — its outputs still appear in the chain (last row). All 8 occupy a chain layer above — no orphans, no removable agents. If an installation has no UI layer (e.g., Java-only consumer per current strategy), `@frontend` simply never gets spawned by `@lead`'s router — the agent stays in the registry as latent capacity, not dead weight.

**Implementer parallelism.** `@backend`, `@frontend`, and `@test` (Stage 1) execute **in parallel** once openapi is locked. `@test` is **spec-bound** in Stage 1 — it reads only openapi-asyncapi / PRD / FRS and cannot read `src/`. Execution graph + two-stage @test detail: §2.ter.

## 2.bis. Diagram bindings (visual proofs)

Diagrams are not decoration; they are the visual proof that an
artifact's claims hold. Each chain layer has named diagram
obligations. All diagrams render as `*.puml` inside a sibling
`diagrams/` folder — `docs/diagrams/` for global, and
`docs/<feature-id>/diagrams/` per-feature — keeping the artifact
root scannable for written work only (see §5b).

| Family | Variant | Lives in | Role |
|---|---|---|---|
| C4 | L1 System Context | SAD | System boundary vs external actors / systems |
| C4 | L2 Container | SAD | Deployable units + their interactions |
| C4 | L3 Component | SAD ↔ TDD bridge | Internal arch of one container (controllers, use cases, repos) |
| C4 | L4 Code | TDD | Class-level UML; usually auto-generated, rarely hand-drawn |
| Sequence | Macro / inter-service | SAD → drives openapi.yaml | Cross-network call chain proves L2 fulfills request; dictates OpenAPI / AsyncAPI |
| Sequence | Micro / intra-service | TDD | Intra-component call chain per use case |
| State | Business | FRS | Domain object lifecycle (e.g., Draft → Pending Approval → Published); validates business rules |
| State | Technical | TDD | Internal lifecycles (circuit breaker, OAuth token, retry FSM) |
| ERD | Conceptual / logical | SAD | Aggregates + entities + relationships; engine-agnostic |
| ERD | Physical | TDD | Concrete schema, FKs, indexes, normalization for one container's datastore |

**Integrated trace** — what each artifact draws as a feature flows through the chain:

```
PRD-NNN  : feature demand
   │
   ▼
FRS-NNN  : feature rules           ← Business State Diagram
   │
   ▼
SAD       : system shape            ← C4 L1 + L2 + Logical ERD
   │
   ▼ (cross-service work)
SAD seq   : Inter-service Sequence  → becomes openapi.yaml (OpenAPI / AsyncAPI)
   │
   ▼
TDD-NNN  : per-service detail      ← C4 L3 + Intra-service Sequence
                                      + Physical DB + Technical State
```

Producer rules:
- @product owns Business State diagrams (FRS-bound).
- @architect owns C4 L1 + L2, Logical ERD, Inter-service Sequence (SAD-bound). See decision §7.25 for prompt-budget split rationale.
- @lead owns C4 L3, Intra-service Sequence, Technical State, Physical DB (TDD-bound).
- Chain-rigor (§4) controls coverage:
  - **Full** — every binding above.
  - **Standard** — skip SAD-only diagrams (C4 L1 / L2, Logical ERD); keep Business State (FRS), Inter-service Sequence (drives openapi.yaml), TDD diagrams.
  - **Light** — TDD diagrams only (C4 L3 if non-trivial, Intra-service Sequence, Physical DB if schema touched, Technical State if applicable).

Render & embed:
- Each `.puml` renders to a paired `.svg` (same basename, same folder); both committed. `.puml` is source-of-truth (diffable, reviewable); `.svg` is what viewers show.
- Producing agent embeds inline via `![title](diagrams/<name>.svg)` in the parent `.md` so the visual proof appears in narrative order with the prose it validates. SVG (not PNG) for text-search, lossless zoom, and native GitHub / GitLab rendering.
- Drift check is filename arithmetic: every `.puml` has a paired `.svg`; every prose artifact citing a §2.bis binding has the matching `![]()` embed line.

## 2.ter. Chain execution and parallelism

§2 lists *what* and *who*. This section lists *when* — which layers run sequentially (data dependency), which fan out in parallel (independence), and which converge.

```
HARD-SEQUENTIAL (lift dependency — each artifact reads the prior one)
  PRD ──→ FRS ──→ SAD ──→ TDD ──→ openapi.yaml | asyncapi.yaml
                  │
                  └─ ADR-NNN.md (parallel with TDD when the decision is
                     independent of TDD content; sequential if TDD informs it)

PARALLEL FAN-OUT (gated on openapi being locked)
  openapi ──┬──→ @backend     ──→ server code + unit tests
            ├──→ @frontend    ──→ UI code + unit tests
            └──→ @test Stage 1 ──→ TSR-NNN.md §test-plan + black-box test code
                                    (SPEC-BOUND; src/ access blocked)

CONVERGE
  All three ──→ @test Stage 2 (impl-aware) + @evaluator + @reviewer
            ──→ TSR-NNN.md (sections: locked) ──→ /orchestra ship
```

**@test is spec-bound in Stage 1.** Authoring runs in parallel with `@backend` and `@frontend`. The agent reads only `openapi.yaml` / `asyncapi.yaml`, PRD, and FRS — `src/` is **blocked at the tool-permission level**, not by prompt convention. Mechanism (per-stage tool scoping, Read-path allowlist, hook-enforced denial) is a `/sc:sc-design` choice; the *requirement* is enforcement, not advisory.

| Stage | Trigger | Sources | Parallel with | Output |
|---|---|---|---|---|
| 1 — spec-driven | openapi locked | openapi/asyncapi, PRD, FRS | @backend, @frontend | TSR-NNN.md §test-plan + black-box test code: HTTP / async behavior, schema validation, contract tests, FRS-rule acceptance scenarios, property-based invariants |
| 2 — impl-aware | impl ready | Stage-1 sources + read access to `src/` | nothing (sequential) | Test execution; impl-aware additions where PRD §NFR demands (race conditions, perf, white-box edges) |

**Why Stage 1 is spec-bound, not advisory:** parallelism (wall-clock); shared-blindspot avoidance (a spec-bound author has never seen the impl, so cannot encode its bugs); **spec-quality forcing function** (if Stage 1 cannot write tests, openapi is underspecified — output is `DEADLOCK-<id>.md` back to `@lead`, not a TODO buried in a test file; the most important benefit); refactor survivability (black-box tests survive impl refactors).

**Other parallelism opportunities:**

- **Within `@lead`, diagram authoring** — `.puml` files in the same phase have no inter-file dependencies (`state-business`, `state-technical`, `sequence-inter-*`, `c4-*`, `erd-*`) and render in parallel.
- **Within an implementer, scoped sub-runs** (BL-0033) — large impl tasks split into N parallel sub-runs, then merged. Same pattern available to `@frontend` and `@test` where workload supports.
- **Cross-feature** — multiple features in one /orchestra run execute their chains in parallel; isolation is the per-feature folder under `docs/<feature-id>/`.

**Anti-parallelism (do not attempt):**

- PRD ‖ FRS — FRS lifts from PRD.
- SAD ‖ TDD — TDD references SAD components.
- TSR sections ‖ impl — verdicts gate on completed impl.
- Stage-2 @test ‖ impl — impl must be runnable to test against.

## 3. Two workflows

**Greenfield** — empty repo. /orchestra runs the chain forward.

**Brownfield** — existing codebase. /orchestra reverse-documents to
user-elected depth, then runs forward chain on every feature thereafter.

## 4. /orchestra entry flow

```
/orchestra (no args)
  │
  ├─ detect mode (empty repo → greenfield; src/ exists → brownfield)
  ├─ mode ambiguous?         → AskUserQuestion: greenfield | brownfield
  ├─ brownfield only?        → AskUserQuestion: depth (light | medium | full)
  ├─ always                  → AskUserQuestion: chain rigor (Full | Standard | Light)
  ├─ greenfield + no lang?   → AskUserQuestion: language + framework
  └─ spawn @lead with locked decisions
```

Chain rigor presets:
- **Full** — all layers (PRD→FRS→SAD→ADR→TDD→openapi)
- **Standard** — skip SAD/ADR (PRD→FRS→TDD→openapi)
- **Light** — TDD only (component-internal change, no spec uplift)

Each ask is **elidable** when its answer is inferable from prompt or
repo state. Plugin asks only when it can't infer.

## 5. Plugin shape

### 5a. Project-side directories — placement rule

Two project-side roots in v4.0. They serve different audiences and different lifetimes — never mix them.

| Root | Audience | Contents | Lifetime |
|---|---|---|---|
| `<project>/docs/` | Humans (PMs, leads, reviewers, ops) | Stakeholder deliverables — every artifact in §2 chain table + diagrams + RELEASE / RUNBOOK | Durable; PR-reviewable; cited across artifacts |
| `<project>/.orchestra/` | Agents + plugin internals | Pipeline-internal coordination + runtime state | Ephemeral or run-bound; never PR-reviewed for content |

| Concern | v3.x | v4.0 |
|---|---|---|
| Plugin runtime (events, tokens, metrics, local.yaml, idempotency registry) | `<project>/.claude/.orchestra/` | `<project>/.orchestra/` |
| Stakeholder deliverables (PRD, FRS, SAD, ADR, TDD, openapi, TSR, RELEASE, RUNBOOK, diagrams) | `<project>/.claude/.orchestra/{architecture,pipeline}/` | `<project>/docs/` |
| Pipeline-internal coordination (intent routing, lead→implementer tasking, escalations, deadlocks) | `<project>/.claude/.orchestra/pipeline/<id>/` | `<project>/.orchestra/pipeline/<id>/` |

**Placement rule.** An artifact lives in `docs/` iff a stakeholder needs to read or cite it. Everything whose only consumer is the next agent in the chain (or the plugin's own bookkeeping) lives in `.orchestra/`. Litmus — would you link it from a PR description for a non-engineer reviewer? `docs/` if yes, `.orchestra/` if no.

### 5b. `<project>/docs/` shape

```
<project>/docs/
├── README.md, CONTRIBUTING.md, SLO.md   ← operational (user-authored, plugin doesn't trample)
├── SAD.md                               ← global (architecture)
├── adr/                                 ← global (architecture); ADRs accrete over project lifetime — decision §7.18
│   └── ADR-NNN.md
├── diagrams/                            ← global; each *.puml has paired *.svg, both committed (see §2.bis)
│   ├── c4-context.puml         + c4-context.svg
│   ├── c4-container.puml       + c4-container.svg
│   └── erd-logical.puml        + erd-logical.svg
└── <feature-id>/                        ← per-feature
    ├── PRD-NNN.md
    ├── FRS-NNN.md              (embeds state-business.svg)
    ├── TDD-NNN.md              (embeds c4-component / sequence-intra-* / state-technical / erd-physical)
    ├── openapi.yaml            (or asyncapi.yaml; embeds sequence-inter-<flow>.svg via description; hosts CONTRACT narrative in description: + # comments — decision §7.23)
    ├── TSR-NNN.md              (multi-writer: §test-plan @test, §verdict-evaluator @evaluator, §verdict-reviewer @reviewer + ADR review — decision §7.21)
    └── diagrams/               ← feature; each *.puml has paired *.svg, both committed
        ├── state-business.puml         + state-business.svg
        ├── sequence-inter-<flow>.puml  + sequence-inter-<flow>.svg
        ├── c4-component.puml           + c4-component.svg
        ├── sequence-intra-<usecase>.puml + sequence-intra-<usecase>.svg
        ├── state-technical.puml        + state-technical.svg          (if applicable)
        └── erd-physical.puml           + erd-physical.svg             (if schema touched)
```

Per-feature prose is **5 files**, not 7: TEST-NNN.md merges into
TSR-NNN.md §test-plan; CONTRACT-NNN.md drops, narrative folds into
openapi.yaml. Decision §7.21.

No `.lock.yaml` siblings. Review state lives in artifact frontmatter
(`status: draft|locked`, `verdict:`, `readers:` allowlist, `sections:`
state map for multi-writer TSR — see §5f); idempotency keys live in
`<project>/.orchestra/manifest.json`; drift detection uses `git diff`
in CI, not file hashes.

### 5b.bis. `<project>/.orchestra/` shape

Sibling tree to §5b's `docs/`. Holds everything the placement rule (§5a) routes off the stakeholder surface.

```
<project>/.orchestra/
├── local.yaml                          ← runtime config (timeouts, model overrides)
├── manifest.json                       ← idempotency registry (replaces lockfile hashes; see §5f)
├── events.jsonl                        ← event log (BL-0032; observability stream 7)
├── metrics/                            ← per-role / per-phase token attribution (BL-0035)
│   └── <run-id>.json
└── pipeline/<feature-id>/              ← per-feature coordination state
    ├── intent.yaml                     ← routing decision (input to @lead)
    ├── TASKS-NNN.md                    ← lead → implementer task breakdown
    ├── DEADLOCK-<id>.md                ← transient; resolved by user intervention or rerun
    ├── ESCALATE-<id>.md                ← transient; covers ARCH / DESIGN variants
    └── ESCALATE-ADR-<NNNN>.md          ← reviewer-flagged retroactive ADR escalation
```

These are agent-to-agent or plugin-internal. They never need PR review and never get cited from `docs/` artifacts. CI may inspect them (e.g., reading `manifest.json` for idempotency or `events.jsonl` for budget burn) — that's tooling, not stakeholder review.

Lifetime notes:
- `intent.yaml` + `TASKS-NNN.md` are run-scoped — kept across reruns of the same feature for idempotency, but not maintained as evergreen docs. Once the feature ships, they're history.
- `DEADLOCK-*.md` / `ESCALATE-*.md` are transient by design — they exist only while a pipeline is stuck and are removed once resolved. A repo with stale escalation files is itself a CI signal.
- `events.jsonl` and `metrics/` accrete; they are observability fuel, not deliverables. Retention policy (rotate / truncate) is a `/sc:sc-design` concern.

### 5c.bis. Consumer CLAUDE.md generation (new feature)

The plugin writes/updates a marked block in `<consumer>/CLAUDE.md` so
Claude Code carries orchestra context **even outside `/orchestra`
invocations**. Closes the "Claude Code without orchestra" gap.

```
<existing user CLAUDE.md content>
<!-- orchestra:start vX.Y.Z -->
... orchestra-managed block ...
- Pipeline artifacts live in <project>/docs/<feature-id>/
- Don't edit artifacts with frontmatter `status: locked`
- Architecture decisions in <project>/docs/SAD.md + <project>/docs/adr/ADR-NNN.md
- For new features, run `/orchestra` first
<!-- orchestra:end -->
```

Idempotent: append on first run; replace block on subsequent runs.
User-authored content outside the block is never touched. Block carries
a version stamp so consumers can spot drift.

## 8.bis. Metrics evidence (v3.x smoke baseline)

A v3.x greenfield smoke run was captured at `/tmp/orchestra-smoke-v3/` (todo-api fixture, 2026-05-07, plugin v2.2.1). It establishes the v4.0 metrics-pipeline requirements with concrete numbers.

**Top-line numbers:**

| Signal | Value |
|---|---|
| Run cost | **$121.90** for one feature run |
| Wall time | 6,903 s (~1 h 55 min) |
| Terminal state | **aborted** — `gates.verdict` + `gates.code_review` left `pending` |
| Subagents spawned | 15 invocations across 6 roles (`@lead`, `@product`, `@backend`, `@test`, `@evaluator`, `@reviewer`) |
| Per-subagent cost range | $0.69 – $8.61 |
| Per-subagent turns range | 4 – 48 |
| Cache_read avg | ~700K tokens / session (caching helps) |
| Cache_create avg | ~95K tokens / session (cache churn nontrivial) |

**The gap.** Primitives are already captured: `events.jsonl` (9 event types), `tokens.jsonl` (per-subagent tokens + usd), `runs/<run-id>.json` (aggregated cost / gates / duration / plugin_version), `insights.jsonl`, `manifest.json`. But three blind spots block attribution: (1) `tokens.jsonl.agent_role` is `"unknown"` in every entry — the hook doesn't read role from the spawn event; (2) `task.subagent.invoked` carries `agent_name` not `subagent_session_id`, so joining role↔cost requires timestamp-order guessing; (3) §2 chain layers appear nowhere in the metric stream, so "which phase burned the budget?" requires hand-mapping. Consequence: the $121.90 aborted run cannot answer cost-by-role or cost-by-phase from data alone.

**v4.0 contract** (drives stream 7):

| Requirement | Why |
|---|---|
| `agent_role` populated on every `subagent.tokens` | Cost-by-role pivot |
| `phase` field added at agent spawn (§2 chain layers) | Cost-by-phase pivot — most actionable view |
| `subagent_session_id` echoed on `task.subagent.invoked` | Direct events↔tokens join |
| Per-artifact token attribution | "What did this PRD cost to write?" |
| `runs/<run-id>.json.status` ∈ {`completed`, `aborted`, `deadlocked`} | Promote terminal state to top-line |
| Reporter tool over `events.jsonl` + `tokens.jsonl` + `runs/*.json` | Workflow timeline `.svg` (Gantt-shape; feasibility already satisfied — only reporter is missing) + cost-by-role / cost-by-phase pivots |

The smoke fixture becomes the **v4.0 regression baseline**: every question above must be answerable from data alone after rework — no timestamp joins, no chain-layer hand-mapping. The committed `aggregated-metrics.html` is cut per §5h; the reporter replaces it on demand.
