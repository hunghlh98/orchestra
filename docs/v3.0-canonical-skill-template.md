# v3.0 canonical skill template

Authoritative shape for `skills/<name>/SKILL.md` after the v3.0.0 prompt-tightening sweep. Companion to `docs/v3.0-canonical-agent-template.md`.

## Audience

Plugin maintainers editing existing SKILL.md files. Consumer-side surface is the rendered SKILL.md; consumers don't see this doc.

## Section sequence

Required sections appear in fixed order. Optional sections appear only when the skill needs them — empty optional sections are forbidden.

| # | Section | Required | Notes |
|---|---|---|---|
| 1 | Identity (1–2 lines after H1) | yes | unmarked — no `## Identity` heading |
| 2 | `## When to use` | yes | bullets, scenarios |
| 3 | `## Approach` OR `## Algorithm` | yes | numbered steps; Algorithm for procedure-only skills, Approach for guides |
| 4 | `## <Reference name>` (e.g. `## Probe DSL`) | optional | lookup tables the skill carries inline |
| 5 | `## Output shape` | optional | for skills producing structured artifacts (frontmatter + body anchors) |
| 6 | `## When to escalate` | optional | failure modes, when NOT to use |
| 7 | `## Worked example` | yes | one concrete walk-through |
| 8 | `## References` | optional | pointers to `references/<file>.md` |

## Per-section rules

### Identity (1–2 lines, no heading)

- ≤2 sentences. State function + consumer agent in one breath.
- No "This skill exists because…" / "The CONTRACT is where ambiguous spec becomes machine-gradable" storytelling.
- ✅ `Produces interfaces/<NNN>-CONTRACT.md. \`@lead\` writes; \`@test\` and \`@evaluator\` consume.`
- ❌ `Produces interfaces/<NNN>-CONTRACT.md: the artifact that binds a feature's success criteria to executable probes. \`@lead\` writes it after PRD/FRS are confirmed; \`@test\` consumes it to write the test plan; \`@evaluator\` uses the criteria + probes to grade. The CONTRACT is where ambiguous spec becomes machine-gradable.`

### When to use

- Bullets only. Each ≤15 words.
- No inter-bullet prose. No "scenarios include:" preamble.
- 2–4 bullets typical; >5 means scope is too wide.

### Approach / Algorithm

- Use **`## Approach`** for skills that guide an authoring task (judgment + procedure).
- Use **`## Algorithm`** for skills that describe a deterministic procedure (no judgment).
- Numbered top-level steps. Step header may be H3 (`### Step 1 — Verb noun`) for guides; flat numbered list for short algorithms.
- Step body: ≤3 sentences OR 1 fenced block + 1 sentence. Fenced YAML/markdown shape allowed inline when load-bearing.
- Drop trailing rationale paragraphs ("If two criteria have the same weight, that's a signal you might be…"). Bake the rule into the step or drop it.

### Reference table / Output shape

- Inline only when the table is load-bearing for the agent reading the skill.
- Deep / edge-case data goes in `references/<file>.md` and is cited from the body.
- Frontmatter shape blocks: fenced YAML, no preamble. The agent reading recognizes `---` shape.

### When to escalate

- Bullets, ≤15 words each.
- Failure modes only — don't restate the Approach as "what to do".
- ✅ `Sum of weights ≠ 100 → surface to @product (likely missing criterion).`

### Worked example

- One example. No "Example A / Example B" branching.
- State input ("PRD says: …") → step output → handoff. Skip narrative bridges between steps.
- The example exists to anchor the Approach; if the Approach is clear, the example can be ≤15 lines.

### References

- Optional. Bullets pointing to `references/<file>.md` files in the same skill directory.
- Drop trailing meta-commentary ("References are conditional; this body covers v1.0.0").

## Drop list (anti-patterns)

| Pattern | Why drop |
|---|---|
| `# <skill-name>` H1 followed by storytelling paragraph | redundant with frontmatter `description`; eats tokens |
| `## Table of Contents` | skills are <500 lines; ToC is overhead |
| `## Best Practices` (when it restates Approach) | duplication |
| `## Resilient workflow` / `## Recovery from failure` | fold into Algorithm steps or move to `references/troubleshooting.md` |
| Inter-step rationale prose | bake into step or drop |
| "You may invoke X" / "You should Y" preambles | imperative voice — say "Invoke X" / "Do Y" |
| Trailing meta-commentary | dead tokens |
| Embedded reference-manual content (>30 lines of lookup prose) | move to `references/<file>.md` |

## Reduction expectations (bimodal, like agents)

| Skill archetype | Expected char reduction |
|---|---|
| Procedure (≤60 lines) | 5–10% — already tight |
| Tool-shaped (100–160 lines) | 10–18% |
| Authoring guide (160–250 lines) | 12–20% |
| Reference manual (>300 lines) | 6–12% body + heavy lift to `references/` |

The line count may not drop; words / chars do. Same lesson as agents.

### AFTER — write-contract (sketch, full rewrite on sign-off)

```markdown
---
name: write-contract
description: "Authors interfaces/<NNN>-CONTRACT.md with weighted criteria, probe DSL, and PASS/FAIL semantics. Use when @lead binds a spec to grading."
origin: orchestra
---

# write-contract

Produces `interfaces/<NNN>-CONTRACT.md`. `@lead` writes; `@test` and `@evaluator` consume.

## When to use

- A `requirements/<NNN>-PRD.md` or `<NNN>-FRS.md` is `confirmed: true` and execution is next.
- An existing CONTRACT needs revision because criteria proved unclear during testing.
- Brownfield migration needs locked acceptance criteria before refactor.

## Approach

### Step 1 — List candidate criteria

Extract every "must"-shaped statement from PRD/FRS. Each becomes one criterion. Aim for 3–8; fewer means under-specified, more means over-specified.

Patterns:
- "X must return Y" → `endpoint.x_returns_y`.
- "After Z, DB shows W" → `persistence.w_after_z`.
- "Adversarial input A → reject with B" → `security.rejects_a_with_b`.
- "Latency p95 < N" → `performance.latency_under_n`.

### Step 2 — Assign weights

Weights sum to 100. Distribute by **business impact**, not implementation difficulty.

| Criterion shape | Typical weight |
|---|---|
| Core behavior | 30–40 |
| Persistence / consistency | 15–25 |
| Security / authentication | 15–25 |
| Performance | 10–15 |
| Idempotency / replay | 10–15 |
| Observability | 5–10 |

### Step 3 — Define probes per criterion

Each criterion gets a `probes:` list using `http_probe` / `db_state`. Probes must be deterministic, self-contained, and assert the criterion (not the implementation).

\`\`\`yaml
criteria:
  transfer.persists:
    weight: 30
    probes:
      - tool: http_probe
        args: {method: POST, url: http://localhost:8080/v1/transfer, body: '{"amount":100,"to":"a2","key":"k1"}'}
        assertions: {status: 201, body_contains: ["transaction_id"]}
      - tool: db_state
        args: {dsn: sqlite3:///tmp/test.db, query: "SELECT amount FROM ledger WHERE key=?", params: ["k1"]}
        assertions: {rows_count: 1, rows[0].amount: 100}
    critical: false
\`\`\`

### Step 4 — Mark critical criteria

`critical: true` triggers feature-level FAIL on miss. Reserve for: security leaks, data-loss paths, compliance-mandated behavior.

### Step 5 — Set passing_score

Default 80. Override only with rationale in body: compliance → 100; beta → 70; migration → 90.

### Step 6 — Write interfaces/<NNN>-CONTRACT.md

Read the dispatcher-scaffolded `pipeline/<feature_id>/interfaces/<NNN>-CONTRACT.md`. Anchors are locked.

Frontmatter (slim, v2.0.0; provenance lives in `<artifact>.lock.yaml`):

\`\`\`yaml
---
id: <NNN>-CONTRACT
type: CONTRACT
created: <ISO-8601>
revision: 1
signed: false
weighted_criteria_total: 100
passing_score: 80
probe_count: <int>
critical_failure_conditions: <int>
---
\`\`\`

Body anchors (locked):
- `S-INTERFACE-001` — HTTP endpoints / events / messages enumerated; reference `<NNN>-API.openapi.yaml` for shape.
- `S-SERVICE-CONTRACT-001` — per-method contract: trigger, payload, success/error, idempotency, ordering. Embed `![Service contract](diagrams/contract-service.svg)`.
- `S-SCORING-001` — integer weights = 100; `passing_score`; critical-fail veto rules. Mirror frontmatter.
- `S-CRITERIA-001` — one C-NNN block per criterion: weight, `critical: true|false`, probe DSL, PASS/FAIL.

Author `diagrams/contract-service.puml` (HTTP + event tables). For each critical-path criterion, author `diagrams/contract-sequence-<criterion-id>.puml`. Invoke `/plantuml` to render `.svg`.

## Probe DSL — quick reference

`tool:` — `http_probe` | `db_state`. `args:` — passed verbatim. `assertions:` — declarative:

- `status: <int>` — HTTP status equality.
- `body_contains: ["str", ...]` — substring match (post-redaction).
- `body_equals: "..."` — full-body equality (brittle; use sparingly).
- `header.<key>: <value>` — header equality.
- `rows_count: <int>` — db_state row count.
- `rows[N].<field>: <value>` — db_state row field.
- `rows_count_at_least: <int>` — db_state min count.

Anything else is documentation, not a machine-gradable assertion. Mark as manual evaluation; let `@reviewer` grade.

## When to escalate

- Sum of weights ≠ 100 → surface to `@product` (likely missing criterion).
- A criterion can't be probed via `http_probe` / `db_state` → mark `manual_evaluation: true`; never fake a probe.
- `passing_score < 70` requested → push back; feature likely under-scoped.

## References

- `references/probe-dsl.md` — full assertion grammar with edge cases.
- `references/criteria-examples.md` — worked CONTRACTs across CRUD, batch, streaming, migration.

## Worked example

`requirements/001-PRD.md`: *"Add `POST /v1/users/:id/transfer`. Records to ledger. Idempotent on `idempotency_key`. Emits `transfer` event. Replay rejected. p95 < 500ms at 100 RPS."*

| ID | Description | Weight | Critical |
|---|---|---|---|
| transfer.persists | endpoint records to ledger | 30 | false |
| transfer.idempotent | same key → single row | 25 | false |
| transfer.emits_event | event_log row appears | 20 | false |
| transfer.rejects_replay | replay → 409 | 15 | **true** |
| transfer.under_500ms | p95 < 500ms at N=100 | 10 | false |

Total 100. `passing_score: 80`. `transfer.rejects_replay` is critical: a replay vulnerability = security regression, single FAIL = no ship. Write per Step 6 shape. Hand to `@test` for `verify/001-TEST.md` via `qa-test-planner`.
```

### What worked

- **`plantuml` 304 → 152 (-50%)** — biggest win. The body had 150+ lines duplicating content already in pre-existing `references/syntax.md` / `references/troubleshooting.md` / 9 other reference files. Deletion was lossless.

- **`write-contract` 203 → 173 (-15%)** — storytelling intro + inter-step rationale removal. All 4 anchors + 7 probe-DSL keys + frontmatter shape preserved verbatim.

### What didn't work

- **Procedure archetype (≤60 lines) often grew, not shrunk.** `shutdown-team` 33 → 38 (+5), `cut-release` 48 → 52 (+4), `resume-pipeline` 54 → 57 (+3). Reason: canonical structure (Identity + When-to-use + Algorithm + Worked example) imposes ~30 lines of fixed overhead. Files already at floor before sweep had no slack to give back. Calling this an "exception" is misleading — it's the floor.
- **Tool-shaped skills compressed only 1–5%, not 10–18%.** Lesson: tool-shaped skills carry per-step procedure mechanics (shape-of-input / shape-of-output) that *are* the load-bearing content. Stripping them to hit a band is rule loss.

### Lesson — bimodal applies to chars, not always lines

Same lesson as agents: line count is a noisy proxy. Word/char drop dominates on rule-preservation-bound files; line drop dominates on duplicated-content files (`plantuml`).

### Lesson — leaky-cite stratification

Streamline fixture's leak detector caught some patterns (`WORKFLOW`, `docs/HOOKS`) but missed others (`DESIGN-NNN-slug §`, `PRD §8.X`, `DESIGN-005-doc-output-overhaul §S-...`). Discovered when re-reading `lockfile.schema.md` for Batch 3.5 and finding L20 leak my earlier regex missed.

**Defense-in-depth grep** that catches the slug-interrupted patterns:
```
grep -rn -E "PRD\s*§|DESIGN-[0-9]+(-[a-z-]+)?\s*§|WORKFLOW-[0-9]+|docs/(PRD|DESIGN|WORKFLOW|HOOKS)" \
  agents/ skills/*/SKILL.md commands/ schemas/
```

Run this before any consumer-surface release. Streamline fixture should incorporate the stricter pattern in v3.x.
