# v4.1 brief - brownfield mode

## Evidence base

Single brownfield pilot: VNG Games Payment System, Order Service reverse-doc.  
Run 3594691f, 22 hours, $132.47, 6 agents, 270 turns, plugin v4.0.6.

## 1. Phase-boundary tagging

**Problem:** 68% of cost attributed to "unknown" phase - lead agent never emits phase events.

**Fix:** Lead agent emits `pipeline.phase.start` / `pipeline.phase.end` at each gate crossing.  
`cost-by-phase.json` aggregates on `phase` key from these events.

Phase taxonomy (brownfield): `discovery`, `spec-draft`, `verification`, `gap-resolution`, `gate`.

**Files:** `hooks/scripts/`, `agents/lead.md`

## 2. Anti-fix-it guardrails

**Problem:** 7 source-code divergences documented; test guards invented ad-hoc to freeze them as intentional.

**Fix:** Add `## Divergences` section to the TSR template. Architect populates it before TSR authoring.  
Row shape: `| ID | UC slug | File:line | Finding | Guard test ID |`

No hook enforcement - the template section is sufficient.

**Files:** `agents/architect.md`, TSR template in `skills/`

## 3. Retroactive ADR phase

**Problem:** 7 new ADRs authored in Phase 3 to ratify gaps - improvised, not a declared pipeline step.

**Fix:** `gap-resolution` as an explicit pipeline phase in brownfield mode.  
Lead hands off to architect with task type `retroactive_adr` after verification gate.  
ADR template gains `## Ratification` section for brownfield divergences.

**Files:** `agents/architect.md`, `agents/lead.md`

## 5. Brownfield bootstrap + workspace topology

**Problem:** Pilot ran `claude` from `new-docs/` (multi-service workspace root) but the in-scope service was `new-docs/project-poc/services/order/`. Bootstrap placed `.orchestra/` at cwd; hooks anchored source_lock to cwd; outputs landed at the wrong scope. No prompt detected the parent-vs-service mismatch. `test_depth` was buried in config with no user prompt.

**Fix:** Bootstrap detects workspace topology and asks for scope **before** locking paths or writing `local.yaml`.

Bootstrap prompt sequence (brownfield branch):
1. `workspace_kind` - AskUserQuestion: `single-repo` / `multi-repo` / `multi-service`
2. `scope_path` - for `multi-*`, AskUserQuestion to pick the in-scope service. Candidate list = walk cwd 2 levels deep for `pom.xml` / `build.gradle` / `package.json` / `go.mod`
3. `test_depth` - explicit `stage1` (contract-only) / `stage2` (impl-aware) choice

`.orchestra/` is two-tier in multi-* workspaces. System-level state lives at `<context_path>/.orchestra/` (workspace registry + metrics rollup across all registered services); per-service chain state lives at `<scope_path>/.orchestra/` (`local.yaml`, `inventory.md`, `run-plan.md`, `pipeline/`, `tasks/`). `source_lock.read_paths` and `source_lock.write_paths` are computed from `scope_path` (schema declared in item #12's allowlist). System-level human outputs (SAD, cross-service ADRs) land at `<context_path>/docs/` per item #9.

`context_path` = session-root captured at `claude` launch (resolves from `${CLAUDE_PROJECT_DIR}` or `pwd`-at-session-start). `scope_path` may equal `context_path` for single-service repos; in that case the two tiers collapse and one `.orchestra/` dir holds everything.

**Two-tier placement:**
- `single-repo` (`scope_path == context_path`) → one `.orchestra/` dir holds both `system.yaml` and `local.yaml`. No migration; no move.
- `multi-repo` / `multi-service` (`scope_path != context_path`) → `<context_path>/.orchestra/` holds `system.yaml` (`workspace_kind`, `context_path`, `registered_services`) + `metrics/` (aggregated). `<scope_path>/.orchestra/` holds `local.yaml` + `inventory.md` + `run-plan.md` + `pipeline/` + `tasks/`. Bootstrap creates each as needed; nothing is moved. Subsequent sessions targeting a different service under the same `<context_path>` auto-register their `scope_path` into `system.yaml.registered_services`.

(Pilot regression: `.orchestra/` was anchored to workspace root despite `pilot_service: order`, so all metrics / deadlocks / escalates for a service-scoped effort lived at system scope. The two-tier split is the structural fix: system-level state stays at context for cross-service rollup, service-level chain state lives at scope.)

**Files:** `commands/orchestra.md`, `agents/lead.md`, `schemas/`

## 6. Round-trip gate

**Problem:** Round-trip (build -> restart -> integration test) documented as a manual TSR procedure, not a pipeline gate. Pilot deferred it with no enforcement mechanism.

**Fix:** `round_trip` becomes an explicit gate state in `local.yaml`. States and the role that drives each transition:

| From | To | Triggered by |
|---|---|---|
| (initial) | `DEFERRED` | Lead, at TSR authoring time when stage-2 round-trip is out of scope |
| `DEFERRED` | `PENDING` | Lead, when a follow-up run or human elects to execute round-trip |
| `PENDING` | `PASS` | Reviewer, on successful build -> restart -> integration test |
| `PENDING` | `FAIL` | Reviewer, on any failure in the chain |

Verdict cannot be `ALLOW` while `round_trip == DEFERRED` - reviewer must emit `ALLOW_WITH_GAP` instead. `ALLOW_WITH_GAP` is a **new v4.1 verdict label**; current schema enumerates `ALLOW` / `REVISE` / `BLOCK`. v4.1 adds `ALLOW_WITH_GAP` to the verdict enum in `schemas/pipeline-artifact.schema.md` alongside the `round_trip` gate field in `schemas/local.schema.json`.

**Files:** `agents/lead.md`, `agents/reviewer.md`, `schemas/pipeline-artifact.schema.md`, `schemas/local.schema.json`

## 7. Hook hardening (inlined from caveman)

Source: https://github.com/JuliusBrussee/caveman - patterns inlined, no runtime dependency.

#### 7a. Symlink-safe file primitives

**Problem:** `metrics-collector.js` uses bare `appendFileSync` on `.orchestra/metrics/*.jsonl`.  
If an attacker creates a symlink at that path (e.g. -> `~/.ssh/authorized_keys`), the hook appends JSONL to it.

**Fix:** Inline caveman's defensive primitives into `hooks/lib/safe-fs.js`:
- `safeAppend(path, line)` - `lstat` + symlink rejection + `O_APPEND` flag + parent-dir ownership check
- `safeRead(path, maxBytes)` - symlink rejection + hard byte cap + returns null on anomaly
- `safeWrite(path, content)` - temp-file + atomic rename + `O_EXCL | O_NOFOLLOW` + 0600 perms

Replace all bare `appendFileSync` / `writeFileSync` calls in `metrics-collector.js` and `agent-plan-sync.js` with these primitives.

**Files:** `hooks/lib/safe-fs.js` (new), `hooks/scripts/metrics-collector.js`, `hooks/scripts/agent-plan-sync.js`

#### 7b. Per-turn pipeline state reinforcement

**Problem:** 22h session, 5 restarts - pipeline phase and active gates drift out of model context across turns.  
Caveman's `UserPromptSubmit` hook re-injects state every turn via `hookSpecificOutput.additionalContext`.

**Fix:** `metrics-collector.js` already subscribes to `UserPromptSubmit`. Extend it:  
On each `UserPromptSubmit`, read `local.yaml` and append to `hookSpecificOutput.additionalContext`:
```
[orchestra] phase: gap-resolution | round_trip: DEFERRED | source_lock: project-poc/**
```
Single line, suppressed if `local.yaml` absent (greenfield pre-bootstrap).

**Files:** `hooks/scripts/metrics-collector.js`

#### 7c. Statusline phase badge

**Problem:** No visual indicator of current pipeline phase during a long session.  
Caveman's statusline reads a flag file and emits an ANSI badge.

**Fix:** Add `hooks/scripts/orchestra-statusline.sh` that reads `<cwd>/.orchestra/local.yaml` and outputs:
```
[ORCH:gap-resolution]
```
Follows caveman's sanitization pattern: whitelist-validate phase name, strip non-alphanumeric, reject symlinks, cap at 64 bytes.  
User wires into statusline config manually (same as caveman - no auto-install).

**Files:** `hooks/scripts/orchestra-statusline.sh` (new)

## 8. Agent writing style - direct prose, no hedging

**Problem:** Authoring agents produce verbose, hedge-heavy prose. Pilot: TDD 604 lines, FRS 392 lines for one service.  
Pattern: "The system shall validate..." / "It should be noted that..." / "may," "might," "could potentially."  
openapi/asyncapi `description:` fields and inline comments carry the same filler.

**Fix:** Add `## Writing style` rule block to `agents/architect.md` and `agents/product.md`:
- Assertions, not descriptions: `"Validates order ID before processing"` not `"The system shall validate the order ID before processing"`
- No section preambles ("This section describes X" -> just start)
- No hedging: `may`/`might`/`could` -> either a hard assertion or drop
- No restatements of prior sections
- openapi/asyncapi `description:` fields: one line max, imperative, no filler

Scope: authoring agents only (architect, product). Reviewer and evaluator use their own formats already.  
Reviewer will check writing style as a named nit category in its spot-check pass.

**Files:** `agents/architect.md`, `agents/product.md`, `agents/reviewer.md`

## 9. Output topology - system vs service vs feature

**Problem:** Pilot produced one flat directory of outputs at the wrong scope. No rule distinguishing system-wide docs (one SAD for the whole payment system) from service-scoped docs (one SAD per service) from feature-scoped docs (PRD/FRS/TDD/CONTRACT/TSR per AI-broken feature). Architect filled the gap by inventing `order-regen-spec.md`.

**Fix:** Three-tier *placement* convention for existing artifact types. No new artifact types - only PRD/FRS/TDD/CONTRACT/TSR/SAD/ADR (already in `schemas/pipeline-artifact.schema.md`).

| Scope | Location | Contents (existing artifact types only) |
|-------|----------|------|
| system | `<context_path>/docs/` | `SAD.md`, `adr/ADR-NNN-*.md`, `diagrams/*.puml` (C4 L1-L2) |
| service | `<scope_path>/docs/` | `SAD.md`, `adr/ADR-NNN-*.md`, `diagrams/*.puml` (C4 L2-L3) |
| feature | `<scope_path>/docs/<feature-slug>/` | `PRD-NNN-*.md`, `FRS-NNN-*.md`, `TDD-NNN-*.md`, `openapi.yaml`, `asyncapi.yaml`, `TSR-NNN-*.md` (per #14) |

Pipeline `<id>` becomes the `<feature-slug>` - one folder per feature, holding the full artifact chain. Runtime state (metrics, deadlocks, escalates) stays under `<scope_path>/.orchestra/`; only human-facing artifacts land in `docs/`.

Pipeline flow:
- **Greenfield:** AI breaks feature -> human reviews -> feature folder lands under `<scope_path>/docs/<feature-slug>/`
- **Brownfield:** AI reads code -> AI breaks feature -> human reviews -> feature folder lands under `<scope_path>/docs/<feature-slug>/`

Placement rules live in `schemas/pipeline-artifact.schema.md` (extended) - no new schema file.

**Negative example (pilot regression):** Service diagrams were written to `project-poc/services/order/diagrams/` - the `docs/` parent was omitted. The bare `<scope_path>/diagrams/` form is forbidden; always `<scope_path>/docs/diagrams/`.

**SAD scope-election:** A workspace-level SAD at `<context_path>/docs/SAD.md` requires its own election step, separate from `scope_path`. When `scope_path != context_path`, the architect must ask whether system-level documentation is in scope or whether only the service-level SAD should be produced. (Pilot regression: SAD landed at workspace `docs/SAD.md` while `pilot_service: order` was set - neither pure-system nor pure-service work, with no explicit decision.)

**Files:** `schemas/pipeline-artifact.schema.md`, `agents/lead.md`, `agents/architect.md`, `agents/product.md`

## 10. C4 component-level discipline

**Problem:** Pilot's brownfield C3 (component) diagrams enumerated every internal class with methods and fields - closer to a UML class diagram than a C4 component view. Brownfield agents have the code in front of them, so the temptation to over-detail is structural, not random.

**Fix:** Add a "C3 is not a class diagram" rule block to `agents/architect.md` and the plantuml skill:
- Cap: 5-10 components per service at C3
- Label by responsibility (`OrderValidator`, `PaymentDispatcher`), not by Java class name (`OrderServiceImpl`)
- No methods, no fields, no parameter lists in C3
- Internal class structure belongs in TDD prose, not in the diagram
- C4 L4 (code-level) is opt-in only - default off for brownfield

Sibling to item #8 (writing style): both constrain agent output shape.

**Files:** `agents/architect.md`, `skills/plantuml/SKILL.md`

## 11. No ad-hoc artifact types - stick to plugin taxonomy

**Problem:** Pilot architect produced `new-docs/project-poc/services/order/order-regen-spec.md` - a freeform file outside the plugin taxonomy. The intake questions it tried to answer (consumer's `regeneration-doc-template.md` fields) all have a home in existing artifacts: PRD body (goals, scope), FRS body (functional decomposition), TDD body (technical mapping), ADR (divergence ratification).

**Fix:** Hard rule in `agents/architect.md`, `agents/lead.md`, `agents/product.md`:

**Allowed filenames under any `docs/` path.** System / service scope:
- `SAD.md`, `adr/ADR-NNN-<slug>.md`, `diagrams/<name>.puml`

Feature scope (`docs/<feature-slug>/`):
- `PRD-NNN-<slug>.md`, `FRS-NNN-<slug>.md`, `TDD-NNN-<slug>.md`, `openapi.yaml`, `asyncapi.yaml`, `TSR-NNN-<slug>.md` (per #14 - `CONTRACT-NNN.md` removed)

**Forbidden:** any other filename pattern. No `*-spec.md`, `*-notes.md`, `*-plan.md`, `*-regen-doc.md`.

**Consumer-supplied brownfield intake templates** (e.g. `regeneration-doc-template.md` at workspace root): architect reads the questions, but answers them inside the **existing artifact bodies** - PRD body for goals/scope, FRS for decomposition, TDD for code mapping, ADR for divergence ratification. Never echo the template back as a new file. (Broader rule: item #15.5 - plugin artifacts never reference legacy paths.)

Enforcement: agent-prompt rule only - no hook guard. Allowed-set listed in architect/lead/product system prompts; reviewer flags violations as a nit category in spot-check.

**Files:** `agents/architect.md`, `agents/lead.md`, `agents/product.md`, `agents/reviewer.md`

## 12. local.yaml schema closure

**Problem:** Pilot wrote freeform fields into `.orchestra/local.yaml` to lock in chain deviations under the guise of user consent:

- `template_deliverable_path: project-poc/services/order/order-regen-spec.md` - invented config field promoting the ad-hoc artifact from item #11 to first-class policy.
- `adapter_notes: "User elected: orchestra standard chain ADAPTED to fill regeneration-doc-template.md v0.3..."` - freeform multi-line prose claiming explicit user consent that was not actually given.
- `chain_rigor: Full`, `spawn_mode: subagent` - additional schema-undefined fields surfaced in the same file.

Because `local.yaml` is read on every restart, an over-eager adaptation persists across sessions and re-establishes itself as policy. Agent-prompt rules from item #11 cannot survive this if config can override them.

**Fix:**
- Both `system.yaml` and `local.yaml` parsers reject unknown top-level fields at load time (strict schema, not lax).
- Forbid freeform-prose fields entirely on either file. No `adapter_notes`. No `User elected: ...` strings anywhere.
- All chain adaptations expressed as schema-validated enums or booleans.
- Bootstrap writes only the allowed allowlist on each file. Chain adaptations require their own gated step with explicit user consent - separate from bootstrap consent - and a corresponding schema field that the validator recognizes.

### Closed allowlist (v4.1)

Two files, two closed allowlists. Unknown fields fail validation at load time on either.

`<context_path>/.orchestra/system.yaml` (workspace-level):

| Field | Type | Source | Default |
|---|---|---|---|
| `workspace_kind` | enum: `single-repo` / `multi-repo` / `multi-service` | bootstrap (item #5) | required |
| `context_path` | path (session-root at `claude` launch) | bootstrap (item #5) | computed |
| `registered_services` | list of `scope_path` | auto-appended on each scope election | `[]` |

`<scope_path>/.orchestra/local.yaml` (per-service):

| Field | Type | Source | Default |
|---|---|---|---|
| `scope_path` | path (subset of `context_path`) | bootstrap (item #5) | computed |
| `test_depth` | enum: `stage1` / `stage2` | bootstrap (item #5) | required |
| `source_lock.read_paths` | list of glob | derived from `scope_path` | computed |
| `source_lock.write_paths` | list of glob | derived from `scope_path` | computed |
| `round_trip` | enum: `DEFERRED` / `PENDING` / `PASS` / `FAIL` | runtime (item #6) | `DEFERRED` |
| `pipeline_id` | string (pre-v4.1 carryover) | bootstrap | required |

Pre-v4.1 fields not listed above are subject to an audit pass before v4.1 release - any field without a v4.1 schema entry is removed from the allowlist (and the writer that emits it is fixed). No grandfathering of unknown fields.

This is the structural enforcement layer behind item #11. Together: #11 stops the lead from *writing* ad-hoc artifacts in the current session; #12 stops the lead from *locking* the deviation across restarts.

**Files:** `schemas/local.schema.json`, `schemas/system.schema.json`, `commands/orchestra.md`, `agents/lead.md`

## 13. Diagram filename allowlist

**Problem:** Pilot produced 46 diagram files for one service across six prefix taxonomies - only three of which are C4-defined:

| Prefix family | Count | C4-defined? |
|---|---|---|
| `c4-l1-context`, `c4-l2-container` (system) | 2 | Yes |
| `C2-container`, `C3-component` (service) | 2 | Yes |
| `C4-code-*` (L4) | 2 | Yes - opt-in per #10 |
| `AD-uc-*` (activity) | 3 | **No - fabricated** |
| `SAGA-*` | 3 | **No - fabricated** |
| `SD-uc-*` (sequence) | 14+ | **No - fabricated taxonomy** |
| `erd-logical`, `sequence-inter-checkout-happy-path` (system scope) | 2 | **No - fabricated** |

Item #10 caps C3 *content* detail. Item #13 caps the *filename allowlist* - what diagram families may exist at all.

**Fix:** Diagrams under any `docs/diagrams/` must match one of:
- `c4-l1-context.puml`
- `c4-l2-container.puml`
- `c4-l3-component.puml`
- `c4-l4-code-<slug>.puml` (opt-in via item #10's flag)

All other prefixes (`AD-*`, `SAGA-*`, `SD-*`, `ERD-*`, etc.) require an explicit `--enable-supplementary-diagrams` flag AND a stated rationale in the relevant ADR or TDD section.

Reviewer flags allowlist violations as a structural failure, not a nit.

**Files:** `agents/architect.md`, `agents/reviewer.md`, `skills/plantuml/SKILL.md`

## 14. Remove `CONTRACT-NNN.md`, promote openapi/asyncapi YAML to first-class artifacts

**Problem:** `CONTRACT-NNN-<slug>.md` was conceived as the "contract artifact" - markdown body with embedded openapi/asyncapi YAML blocks. In practice the role doesn't survive contact with the work:

- Brownfield reverse-doc: openapi/asyncapi are extracted directly from Spring annotations / generators. The markdown wrapper duplicates the YAML with no information gain.
- Greenfield design: when an agent authors the contract, the YAML itself is the source of truth. A markdown wrapper either restates it (drift hazard) or carries narrative that belongs in TDD.
- Acceptance criteria, breaking-change policy, and versioning - the three things the markdown wrapper *could* uniquely carry - all have better homes: PRD (AC is a product concept), ADR (each breaking change is a decision), and `info.version` in the YAML itself.

The pilot confirmed the misfit: it skipped `CONTRACT-NNN.md` entirely and produced sibling `001-order-regen-openapi.yaml` + `001-order-regen-asyncapi.yaml`. The agent's instinct was right; the plugin's instinct was wrong.

**Fix:** Drop `CONTRACT-NNN-<slug>.md` from the artifact taxonomy. Promote `openapi.yaml` and `asyncapi.yaml` to first-class artifacts under the feature folder, with fixed filenames (no `-NNN` numbering - one openapi + one asyncapi per feature, max).

Taxonomy shrinks from 7 -> 6 artifact types: `SAD`, `ADR`, `PRD`, `FRS`, `TDD`, `TSR`. The artifact chain becomes: PRD -> FRS -> TDD -> (openapi/asyncapi as needed) -> TSR.

### Content displacement map

| What `CONTRACT-NNN.md` carried | New owner |
|---|---|
| Wire schema | `openapi.yaml` / `asyncapi.yaml` directly |
| Acceptance criteria | PRD body |
| Breaking-change policy | ADR (one ADR per breaking change) |
| Versioning rule | `info.version` field in the YAML |
| Narrative around the contract | TDD body |

### Reviewer rules (replace existing CONTRACT-NNN gate)

- When PRD/FRS reference a REST surface, `openapi.yaml` must exist in the feature folder.
- When PRD/FRS reference messaging, `asyncapi.yaml` must exist.
- YAML files are themselves gated artifacts (validated against openapi/asyncapi spec versions declared in the schema).
- TSR test plan references the YAML directly, not a CONTRACT-NNN.md.

### Migration path for existing consumers

This is a breaking change. v4.1 RELEASE note:
- Pre-v4.1 `CONTRACT-NNN-<slug>.md` files are legacy artifacts. Plugin no longer authors them.
- Consumers can keep existing files for history (plugin ignores them) or extract their embedded YAML into `openapi.yaml` / `asyncapi.yaml` siblings.
- No automated migration tool - manual one-time edit.

### Cross-references

- Item #9 (output topology) - feature-folder filename list updated to reflect YAML promotion.
- Item #11 (no ad-hoc artifacts) - allowlist updated; `openapi.yaml` / `asyncapi.yaml` join the permitted set.
- Item #12 (local.yaml schema) - `contract_format` field unnecessary; YAML is the only contract format.

**Files:** `schemas/pipeline-artifact.schema.md`, `agents/architect.md`, `agents/product.md`, `agents/reviewer.md`, `skills/write-contract/SKILL.md` (rename or rewrite), `CLAUDE.md` (project-local - taxonomy noun list)

## 15. Brownfield workspace inventory + migration plan

**Problem:** The pilot workspace had 21 top-level entries before bootstrap ran. Bootstrap inventoried none of them.

Pre-existing at `new-docs/` (May 5 timestamps, before plugin touched anything):

- **9 doc directories**: `adr/`, `api-contracts/`, `archive/`, `database/`, `events/`, `mock-services/`, `money-flow/`, `review/`, `schedules/`, `sequences/`, `state-machine/`
- **4 root-level diagrams**: `ContainerDiagram-WebShop.puml`, `ContainerDiagram.puml`, `ServiceCatalog-WebShop.puml`, `project-dependencies.puml`
- **2 SAD-equivalent files**: `HighLevelDesign.md` (66 KB), `HighLevelDesign-WebShop.md` (216 KB) - likely two versions of the same content
- The codebase: `project-poc/`

Bootstrap plowed past all of it. The plugin authored `docs/SAD.md` (collides semantically with the existing `HighLevelDesign.md` - no detection, no reconciliation), produced 15 ADRs (may overlap with the pre-existing `adr/` dir contents - no cross-check), and wrote diagrams to `docs/diagrams/` (parallel taxonomy to the root-level `*.puml` files - no migration).

The user's actual intent for a brownfield reverse-doc run is *"restructure this chaotic doc tree into the plugin's format."* That intent has no machinery today.

**Fix:** Bootstrap (item #5) gains a pre-regen discovery phase. Before any chain artifact is authored, the lead invokes a new `skills/brownfield-inventory/SKILL.md` that does the following:

### 1. Adaptive-depth structure scan

Run `tree -L N` with progressive depth on `context_path`:
- L1 -> top-level shape
- L2 -> descend if doc-bearing dirs exist at L1
- L3 -> descend if multi-service markers (`services/`, `packages/`, `pom.xml` at multiple depths)
- L4-L5 -> only when L3 is still ambiguous

Stop as soon as the structure is legible. Hard cap at L5. Exclude `.git`, `node_modules`, `target`, `build`, `dist`, `.idea`, `.venv`, plus anything outside `source_lock.read_paths`.

### 2. Classify each entry against plugin taxonomy

Every top-level doc-bearing path lands in one of four buckets:

| Bucket | Definition | Examples from pilot |
|---|---|---|
| **plugin-equivalent** | Maps cleanly to an existing plugin artifact | `HighLevelDesign.md` -> SAD candidate; `adr/` -> `docs/adr/`; root-level `*.puml` -> `docs/diagrams/` |
| **out-of-taxonomy** | No plugin artifact covers this content | `money-flow/`, `state-machine/`, `mock-services/`, `schedules/`, `events/` |
| **redundant** | Overlaps another entry in the same workspace | `HighLevelDesign.md` + `HighLevelDesign-WebShop.md`; `ContainerDiagram.puml` + `ContainerDiagram-WebShop.puml` |
| **stale** | Dated filenames, archive markers, supersession patterns | `archive/`, `old-*`, `*-todo.md`, dated `YYYYMMDD-*` files |

**Classification heuristics** (encoded in the skill body, applied in order; first match wins):

| Signal | Bucket | Notes |
|---|---|---|
| Two files share a base name with a suffix variation (`HighLevelDesign.md` + `HighLevelDesign-WebShop.md`; `ContainerDiagram.puml` + `ContainerDiagram-WebShop.puml`) | **redundant** | Larger / more-recently-modified file wins as canonical; smaller archived |
| Filename or dir name contains `archive`, `old-`, `deprecated`, `legacy`, or matches dated prefix `YYYY-MM-DD-` / `YYYYMMDD-` | **stale** | Skip content sniff; user confirms archive in step 3 |
| Filename matches `HighLevelDesign*.md`, `architecture*.md`, `SAD*.md`, `system-design*.md` **OR** `.md` first 30 lines contain >=2 of: `# Architecture`, `# Container`, `# Component`, `## Context`, `## Containers`, `## Components` | **plugin-equivalent** -> SAD | Content-sniff overrides filename-only when both signals disagree |
| Directory in {`adr/`, `decisions/`, `arch/decisions/`, `architecture-decisions/`} **OR** `.md` first 20 lines match ADR template signature (>=3 of: `## Status`, `## Context`, `## Decision`, `## Consequences`, numbered `ADR-NNN`) | **plugin-equivalent** -> ADR | Classify per-file inside the dir |
| File extension in {`.puml`, `.plantuml`, `.mmd`, `.drawio`} located outside `docs/diagrams/` | **plugin-equivalent** -> diagram | Subject to item #13 filename allowlist on migration |
| Directory exists at workspace root, doc-bearing (contains `.md` / `.puml` / `.yaml`), and none of the above match | **out-of-taxonomy** | User decides target plugin artifact in step 3 |

Heuristic confidence: filename-only matches are LOW confidence; filename + content-sniff agreement is HIGH; content-sniff override of filename surfaces a one-line warning row in `inventory.md` for the user to review.

**Empty-workspace short-circuit:** if the depth-limited scan finds no doc-bearing dirs and no SAD-equivalent files at L1-L3, skip steps 2-4 and emit an empty `inventory.md` stub. Chain proceeds as if greenfield.

### 3. Present inventory and elicit migration decisions

Lead presents the classified inventory as a structured table and, per bucket, asks the user:

- **plugin-equivalent** -> migrate as regen seed (chain reads it as input) / keep as legacy reference / discard
- **out-of-taxonomy** -> fold into a plugin artifact (which one?) / keep as legacy under `legacy/` / archive
- **redundant** -> pick canonical, archive the rest
- **stale** -> confirm archive, no further action

Use `AskUserQuestion` one bucket at a time. Skip buckets that are empty.

### 4. Emit a migration plan

Output: `<scope_path>/.orchestra/inventory.md` - schema-validated, not freeform - containing:
- The scan output (depth-limited tree)
- The bucketed classification
- The per-entry decision (action + target path)
- The regen plan: which features will be authored, which legacy docs seed each feature

User gates on `inventory.md` before any chain runs. Chain agents read this file at start-of-run to know what legacy material to consult.

### 5. No-residual-link rule

After migration, plugin-generated content references only paths under `<scope_path>/docs/**` and `<scope_path>/.orchestra/**` (and the workspace equivalents). It does NOT reference legacy paths outside that boundary.

**Migration is content extraction, not linking.** When inventory classifies a legacy file as a regen seed, the agent reads its content, re-authors the relevant material into a plugin artifact (PRD body, TDD prose, ADR ratification), and then archives or deletes the source. Plugin artifacts must not contain `[see HighLevelDesign.md](../HighLevelDesign.md)`-style backreferences - the legacy file has no continuing role in the structured doc tree.

**Legacy archive location:** files marked "archive" go to `<scope_path>/.orchestra/legacy/` (or `<context_path>/.orchestra/legacy/` for system-scope legacy). This keeps the workspace tidy and ensures all plugin-touched paths live under `.orchestra/` or `docs/`.

**Where legacy references are permitted (exhaustive list):**
- `<scope_path>/.orchestra/inventory.md` - the one-time discovery record. References legacy paths because that's literally its job.
- Migration commit messages and PR descriptions - same rule as dev-trace cites in CLAUDE.md section "Where dev-trace cites SHOULD go".

**Nowhere else.** Not in PRD, FRS, TDD, TSR, SAD, ADR, openapi.yaml, asyncapi.yaml. Reviewer flags any plugin-output path that escapes the `docs/` + `.orchestra/` boundary as a structural failure.

This rule is the runtime analog of CLAUDE.md's consumer-vs-developer surface rule: just as consumer surface must not cite dev-surface, plugin chain artifacts must not cite pre-plugin legacy. Same audience-boundary principle, one step further downstream.

### 6. Why this is P0

Without inventory, every brownfield run has the pilot's failure mode: structure-blind authoring producing duplicates, collisions, and unreconciled parallel taxonomies. Items #5, #9, #11 cannot do their work in a brownfield workspace until #15 establishes the map.

### Cross-references

- Item #11 (no ad-hoc artifacts) - #15's classification uses the allowed-set defined there.
- Item #12 (local.yaml schema closure) - `inventory.md` schema follows the same strict-validation rule; no freeform prose.

**Files:** `skills/brownfield-inventory/SKILL.md` (new), `commands/orchestra.md`, `agents/lead.md`, `schemas/inventory.schema.md` (new)

## 16. Run-plan + plan-gated auto-mode

**Problem:** After bootstrap (#5) and inventory (#15) detect workspace topology and classify legacy material, the chain begins authoring without surfacing the full plan of work to the user. Each phase raises its own `AskUserQuestion` gates; the user accumulates context piecewise across many turns and never sees the run end-to-end. There is no upfront contract the user can review — every gate is a separate trust grant. End-to-end autonomous execution is structurally unavailable.

**Fix:** After bootstrap + inventory complete, lead authors `<scope_path>/.orchestra/run-plan.md` — a single document showing what the chain will produce, in what order, with what gates. Brownfield: lead enters Claude Code plan mode (`EnterPlanMode`) to verify the inventory's regen feature list against actual source under `<scope_path>/src/**`, then `ExitPlanMode` triggers Claude Code's native plan-approval pane. Greenfield: lead authors directly; dispatcher gates approval via `AskUserQuestion(approve|revise)`. Approval flips `auto_mode: true` in `local.yaml`; chain runs end-to-end without between-phase prompts. Reviewer `REVISE` / `BLOCK` verdicts and structural-allowlist halts still pause the chain — auto-mode skips advisory gates, not failure gates.

### run-plan.md content (required anchors)

- `S-CONTEXT-001 — ## Context` — `primary_language`, `framework`, `workspace_kind`, `scope_path`, `test_depth`, lifted from `local.yaml`.
- `S-PHASES-001 — ## Phases` — sequence per #1 taxonomy (`discovery` → `spec-draft` → `verification` → `gap-resolution` → `gate`) with planned agents per phase.
- `S-FEATURES-001 — ## Features` — per-feature rows: `| Feature slug | Authoring agents | Artifacts | Legacy seeds (from inventory.md) |`. For brownfield runs, rows are pre-populated from `inventory.md`'s regen-plan section.
- `S-GATES-001 — ## Gates` — which gates remain manual under auto-mode (reviewer `REVISE` / `BLOCK`, structural-allowlist violations per #11 / #13, schema-validation failures) vs which are auto-passed (between-phase "proceed?" prompts, per-feature confirmation, autonomy-ladder `DRAFT_AND_GATE` checkpoints).
- `S-APPROVAL-001 — ## Approval` — `plan_status: drafted | approved | revision_requested`. User sets this; reviewer-as-nit validates structural shape only.

### local.yaml additions (extends #12 allowlist)

| Field | Type | Source | Default |
|---|---|---|---|
| `auto_mode` | boolean | lead, at plan approval | `false` |
| `run_plan_status` | enum: `drafted` / `approved` / `revision_requested` | lead, at plan emission; user, at approval | absent |

Invariant: `auto_mode: true` requires `run_plan_status: approved`. Validator enforces the pairing — `auto_mode: true` without `run_plan_status: approved` fails schema load.

### Bootstrap sequence (extends #5)

1. `workspace_kind` (existing)
2. `scope_path` (existing)
3. invoke inventory skill (#15)
4. `test_depth` (existing)
5. **NEW: invoke run-plan-author** — lead reads bootstrap fields + `inventory.md`. **Brownfield:** lead `EnterPlanMode`, explores `<scope_path>/src/**` to verify regen features against actual source, authors plan body in plan mode, `ExitPlanMode` for native approval; on accept lead writes `run-plan.md` at the canonical path. **Greenfield:** lead authors `run-plan.md` directly; dispatcher gates via `AskUserQuestion(approve|revise)`. On approval (either branch), dispatcher writes `auto_mode: true` + `run_plan_status: approved` to `local.yaml`. On rejection, dispatcher writes `run_plan_status: revision_requested` and re-spawns lead with `revision_notes`.

### Auto-mode runtime semantics

Skipped under `auto_mode: true`:
- Between-phase "proceed?" gates.
- Per-feature confirmation prompts.
- Autonomy-ladder `DRAFT_AND_GATE` checkpoints at intermediate artifacts (PRD/FRS/TDD draft acceptance).

Preserved under `auto_mode: true`:
- `REVISE` / `BLOCK` verdicts from reviewer.
- Structural-failure halts: allowed-set violations (#11), diagram-allowlist violations (#13), schema-validation failures.
- `ESCALATE` / `DEADLOCK` artifact emission (pipeline aborts as today).

`auto_mode` is per-run. Each new `pipeline_id` starts at `auto_mode: false` until its own `run-plan.md` is approved. User may flip `auto_mode: false` at any time mid-run to revert to gated execution.

### Why P1

UX feature compounding with #15. Without #16, brownfield runs work but require many per-phase confirmations even after the user has already approved the regen plan in `inventory.md`. With #16, plan approval is the single trust contract for a multi-feature run.

### Cross-references

- #1 (phase tagging) — `run-plan.md` enumerates the phases that `pipeline.phase.start` / `pipeline.phase.end` events tag.
- #5 (bootstrap) — run-plan author is step 6 in the bootstrap sequence; uses fields locked by steps 1-5.
- #11 (no ad-hoc artifacts) — `run-plan.md` joins the allowed-set as a singleton at `<scope_path>/.orchestra/`.
- #12 (local.yaml closure) — `auto_mode` + `run_plan_status` join the closed allowlist; validator enforces the pairing.
- #15 (inventory) — `inventory.md`'s regen-plan rows feed `run-plan.md`'s `S-FEATURES-001` table.
