# v5.0 — Feature DAG + Role Reassignment (Requirements Brief)

Status: requirements discovery complete. Design + implementation gated on human review.

## Problem

Today orchestra has no inter-feature dependency model. Two consequences:

1. **Mixed PRDs.** One PRD can describe two distinct capabilities. Reverting either is destructive — the other capability lives in the same artifact and same commits.
2. **Implicit coupling.** Downstream features silently depend on upstream features (shared DB row, undeclared HTTP call, internal module import). Revert of upstream breaks downstream without warning.

Symptom: refactoring a "feature" requires reading the entire `docs/` tree to discover what touches what. No machine-checkable boundary.

## Goals

G1. Each `<feature-id>` is a single-concept node. One PRD describes one capability.
G2. Inter-feature relationships are declared in a manifest, not inferred from code.
G3. Manifest makes revert-safety explicit. Mechanical revert is user-owned (orchestra ships no revert command in v5.0).
G4. Every new requirement triggers an `AskUserQuestion` confirming whether it relates to existing features. Yes → list edges. No → standalone.
G5. Role responsibilities are explicit and non-overlapping. Each artifact has one author role. Adjacent roles connect via dispatcher-owned handoff gates (FR-9).
G6. Feature graph is append-only. Modifications to existing behavior land as new feature-ids with `depends_on:` edges, not in-place edits of old PRDs.

## Two DAGs

### Feature DAG — spec layer

Nodes = `<feature-id>` (e.g., `001-user-registration`). Edges = `depends_on` declared in manifest. Acyclic. Append-only. Validated on every manifest write.

### Role DAG — process layer

Nodes = agents. Edges = artifact handoffs. One author per artifact type.

Gates marked `[GATE]` are dispatcher-owned `AskUserQuestion` checkpoints. Mechanical transitions (no marker) auto-advance on artifact lock.

```
User intent
    │
    ▼
Dispatcher: LLM classify tech | business
    [GATE 1]  tech | business confirmation (AskUserQuestion on uncertain)
    │
    ├── tech ──────────────────────────────────────────────┐
    │                                                       │
    └── business                                            │
            │                                               │
            ▼                                               │
        @product                                            │
            owns: PRD, features.yaml entry                  │
            │                                               │
            ▼                                               │
    [GATE 2]  PRD review → proceed to FRS?                  │
            │                                               │
            ▼                                               │
        @analyst   (BR ↔ AC ↔ pseudocode bridge)            │
            owns: FRS                                       │
            │                                               │
            ▼                                               │
    [GATE 3]  FRS review → proceed to TDD?                  │
            │                                               │
            ▼                                               │
        @architect                                          │
            owns: TDD, openapi, SAD, ADR, business-invariants
            also: source-code exploration on brownfield     │
            │                                               │
            ▼                                               │
    [GATE 4]  TDD + openapi review → proceed to impl?       │
            │                                               │
            ▼                                               │
        @lead  (orchestrator only)  ◄───────────────────────┘
            owns: task-breakdown, run-plan, TASKS
            │
            ▼
    [GATE 5]  run-plan approval (existing forward-chain gate)
            │
            ▼
        parallel:  @backend  ‖  @frontend  ‖  @test-author
            │

            │
```

## Functional requirements

### FR-1. Feature manifest

- `.orchestra/<service>/features.yaml` exists per service.
- Schema: closed allowlist via `schemas/features.schema.json`.
- Shape:
  ```yaml
  features:
    - id: <NNN-slug>
      status: active | deprecated
      depends_on: [<feature-id>...]
      supersedes: [<feature-id>...]        # optional; declared by successor only
      artifacts: [PRD, FRS, TDD, openapi, TSR]
  ```
- DAG validation on write: no cycles, all `depends_on` and `supersedes` IDs exist, no self-edges.
- Append-only: entries never deleted. User marks `status: deprecated` explicitly; orchestra never auto-flips status.
- Successor link: when a new feature declares `supersedes: [<old>]`, orchestra surfaces this on read but does not edit `<old>`.
- Written via `orchestra-utils` MCP closed-allowlist tool (new: `upsert_features_yaml`).

### FR-2. Tech-vs-business classifier

- Runs in dispatcher (main thread) on every `/orchestra <intent>` invocation.
- Pure LLM classification. No regex heuristic.
- LOW or MEDIUM confidence → `AskUserQuestion` with `tech | business` options.
- Default-business rule: any user-visible surface change routes business, regardless of phrasing.
- Tech path admits: dependency bump, lint fix, internal refactor with zero contract change, observability tweak, build tooling.
- Tech path still creates a `<feature-id>` for tracking. Shares the same `NNN-slug` namespace as business features — one counter, no separate range.

### FR-3. @product — PRD + manifest entry

- Reads `features.yaml` + existing `docs/<feature-id>/*-PRD.md` before drafting.
- **Always** opens with `AskUserQuestion`, regardless of confidence:
  > "Does this requirement relate to any existing feature? If yes, which?"
- User answer determines:
  - "No" → `depends_on: []`. Standalone feature.
  - "Yes, [feature-ids]" → `depends_on: [<ids>]`. New node, edges to listed upstreams.
- No tri-state classification. No in-place modification path — every new behavior is a new feature-id.
- Writes manifest delta + `<feature-id>-PRD.md` in one turn.

### FR-4. @analyst — new agent

- Bridges business intent ↔ technical pseudocode. Authors FRS only.
- Inputs: PRD.
- Outputs: `<feature-id>-FRS.md` containing BR (business rules) + AC (acceptance criteria) + pseudocode where it sharpens AC.
- Tool surface: Read, Write, Edit, AskUserQuestion, Skill. No Bash. No `src/` write.
- Reference content: `skills/business-analysis/` authored in orchestra voice (patterns adapted from public BA practice; no verbatim vendoring).
- Uses `AskUserQuestion` at ambiguity. Frequency governed by `hooks/scripts/val-calibration.js` autonomy tier.

### FR-5. @architect — expanded scope

- Owns ALL architecture artifacts:
  - System-wide (multi-repo workspaces only): SAD, ADR, business-invariants.
  - Per-feature (always): TDD, openapi.yaml.
- Inputs: PRD + FRS (+ SAD when system-wide).
- Brownfield: owns source-code exploration. Reads `src/**` to derive TDD + openapi on reverse-pass.
- Uses `AskUserQuestion` at ambiguity. Frequency governed by `hooks/scripts/val-calibration.js` autonomy tier.

### FR-6. @lead — pure orchestrator

- No artifact authorship except TASKS and `run-plan.md`.
- Inputs: TDD (business path) | intent (tech path).
- Spawns parallel fan-out: `@backend`, `@frontend`, `@test-author`.
- Manages converge: `@test-runner` → `@evaluator` + `@reviewer`.
- Tech path: receives intent directly when no design surface changes. If mid-task discovers contract change → escalates to `@architect`, halts implementation.
- Uses `AskUserQuestion` at ambiguity. Frequency governed by `hooks/scripts/val-calibration.js` autonomy tier.

### FR-7. Mixing guard

- `@product` PRD-author prompt: one PRD = one capability.
- Detection: if drafted PRD's AC list spans concepts that exist as separate manifest entries OR look mergeable into ≥2 entries, `@product` MUST `AskUserQuestion` to split.
- No `status: pending`. No "review later" flag. Decision is upfront.

### FR-8. Brownfield reverse flow

- Same Role DAG, reversed direction:
  - `src/**` → `@architect` (extract TDD + openapi, source-code exploration is part of role)
  - → `@analyst` (derive FRS)
  - → `@product` (synthesize PRD + manifest entry)
- `features.yaml` derived from existing `docs/<feature-id>/` directories on first reverse pass.
- Handoff gates apply in reverse: TDD/openapi review → FRS review → PRD review. Plus the existing reverse-pass plan-mode gate (`run-plan-gate-mode-split`).

### FR-9. Handoff gates (dispatcher-owned)

Five gates total. All AskUserQuestion calls live in the dispatcher (main thread), never in upstream agents.

| Gate | Trigger | Question |
|---|---|---|
| 1 | `/orchestra <intent>` | Tech or business path? (LOW/MEDIUM confidence only) |
| 2 | `@product` returns PRD-locked | Proceed to FRS authoring? |
| 3 | `@analyst` returns FRS-locked | Proceed to TDD + openapi authoring? |
| 4 | `@architect` returns TDD + openapi locked | Proceed to implementation orchestration? |
| 5 | `@lead` returns run-plan draft | Approve run-plan? (existing forward-chain gate) |

Auto-advance transitions (no gate): fan-out → `@test-runner` → `@evaluator` + `@reviewer` → TSR lock.

Rationale: gates 2/3/4 catch wrong-direction work before downstream labour starts. Gate 5 (run-plan approval) doubles as the fan-out gate — no redundant confirm.

## Non-functional requirements

NFR-1. Manifest writes go through MCP closed-allowlist. No raw `Write`/`Edit` on `features.yaml`.
NFR-2. DAG cycle check runs at write time, not lint time. Cycle = write refused.
NFR-3. Tech-path classification false-negative (business intent routed tech) is the failure mode to minimize. Tune default toward business.
NFR-4. Brief stays under 600 lines including all schemas. v5.0 is a refactor, not a green field — only describe deltas from v4.x.

## Out of scope (explicit)

- Cross-service feature DAG. v5.0 covers intra-service relationships only.
- Mechanical revert automation (commands, refuse-on-downstream cascade). Manifest carries enough information for a future tool; v5.0 does not ship one.
- Feature-folder code architecture (`src/features/<id>/`). One source tree, normal layout.
- BPMN / process modeling output from `@analyst`. FRS only.
- Automatic feature-id slug generation. User supplies the slug; `@product` confirms.
- In-place modification of existing PRDs. Append new feature-id with `depends_on:` edge instead.

## Acceptance criteria

AC-1. New `<feature-id>` cannot be created without a manifest entry.
AC-2. Manifest write with a cycle is refused by the MCP tool.
AC-3. `@product` first turn opens with `AskUserQuestion` on every invocation.
AC-4. `@analyst` agent file exists with correct tool surface (no Bash, no src write).
AC-5. `@architect` agent file lists openapi + TDD + brownfield code-exploration as owned responsibilities.
AC-6. `@lead` agent file removes openapi/TDD authorship; retains orchestration + TASKS only.
AC-7. Dispatcher tech-vs-business classifier path documented and exercised in smoke test.
AC-8. Brownfield reverse pass produces a complete `features.yaml` from existing `docs/` on first run.
AC-9. Tech-path intents produce a manifest entry (per FR-2).
AC-10. `skills/business-analysis/` exists, authored in orchestra voice.
AC-11. Dispatcher exposes 5 handoff gates per FR-9. Gates 2/3/4 fire on artifact lock; gate 5 is the run-plan approval already shipped.
AC-12. `@analyst`, `@architect`, `@lead` use `AskUserQuestion` within their turns, calibrated by val-calibration autonomy tier.
AC-13. Manifest schema supports `supersedes:` field. Successor declaration leaves predecessor `status` untouched.
