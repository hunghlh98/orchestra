# v5.0 — Feature DAG + Role Reassignment (Design)

Companion to `docs/v5.0-feature-dag-brief.md` (requirements). This doc carries concrete shapes: schema JSON, MCP tool signatures, agent prompt deltas, dispatcher classifier prompt, gate wiring. One doc per `single-comprehensive-design-doc` rule.

## Overview

v5.0 ships **one new agent** (`@analyst`), **one new schema** (`schemas/features.schema.json`), **one new MCP tool** (`orchestra-utils.upsert_features_yaml`), **one new skill** (`skills/business-analysis/`), and **five new dispatcher gates** (FR-9). Three existing agents (`@product`, `@architect`, `@lead`) get prompt rewrites for the role reassignment. Everything else (`@backend`, `@frontend`, `@test-author`, `@test-runner`, `@evaluator`, `@reviewer`, the 7 hooks, the 2 MCP servers' other tools) stays as today.

## 1. Schema — `schemas/features.schema.json` 

#comment this can be generated by MCP ?

JSONSchema Draft-07. Closed allowlist. Carries shape only — no `$comment`, no version stamps, no rule duplication from brief.

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "features.yaml manifest",
  "type": "object",
  "required": ["features"],
  "additionalProperties": false,
  "properties": {
    "features": {
      "type": "array",
      "items": { "$ref": "#/definitions/feature" }
    }
  },
  "definitions": {
    "feature_id": {
      "type": "string",
      "pattern": "^[0-9]{3}-[a-z0-9]+(-[a-z0-9]+)*$"
    },
    "feature": {
      "type": "object",
      "required": ["id", "status", "depends_on", "artifacts"],
      "additionalProperties": false,
      "properties": {
        "id":         { "$ref": "#/definitions/feature_id" },
        "status":     { "enum": ["active", "deprecated"] },
        "depends_on": { "type": "array", "items": { "$ref": "#/definitions/feature_id" } },
        "supersedes": { "type": "array", "items": { "$ref": "#/definitions/feature_id" } },
        "artifacts":  { "type": "array", "items": { "enum": ["PRD", "FRS", "TDD", "openapi", "asyncapi", "TSR"] } }
      }
    }
  }
}
```

Acyclicity, edge-existence, self-edge, and uniqueness-by-id are **not** expressible in JSONSchema. The MCP tool enforces all four imperatively (see §2).

Status transitions are user-controlled, bidirectional (`active ↔ deprecated`). Orchestra never auto-flips. `supersedes` is an independent forward-pointer for read-side surfaces — it does **not** imply `depends_on`. A successor that wants strict edge enforcement must declare both `supersedes:` and `depends_on:`.

## 2. MCP tool — `orchestra-utils.upsert_features_yaml`

Lives under existing `orchestra-utils` MCP server. Closed-allowlist write — no raw `Write`/`Edit` on `features.yaml` per NFR-1.

### Signature

The MCP server registers both schemas with `ajv.addSchema()` at startup so the `$id`-anchored ref resolves uniformly. The tool's `inputSchema` references the `feature` definition by its absolute schema id, not by file path:

```typescript
// At server startup
ajv.addSchema(require("./schemas/features.schema.json"), "https://orchestra/schemas/features.schema.json");

// Tool registration
{
  name: "upsert_features_yaml",
  description: "Insert or update one feature entry in .orchestra/<service>/features.yaml. Validates JSONSchema, DAG acyclicity, edge existence, uniqueness. Returns the persisted entry or a structured error.",
  inputSchema: {
    type: "object",
    required: ["service", "feature"],
    additionalProperties: false,
    properties: {
      service:  { type: "string", pattern: "^[a-z0-9-]+$" },
      feature:  { "$ref": "https://orchestra/schemas/features.schema.json#/definitions/feature" }
    }
  }
}
```

### Behavior (pseudocode)

```
0. Load existing file as YAML; if absent, init with { features: [] }
   - Reject load if duplicate ids present in features[] (UNIQUENESS_VIOLATION)
1. Resolve path: <cwd>/.orchestra/<service>/features.yaml
2. Validate input feature against features.schema.json (feature definition)
3. Upsert into features[] array — replace if id matches, else append
4. Re-validate full file against features.schema.json
5. DAG checks (imperative):
   a. Edge existence — every id in feature.depends_on and feature.supersedes
      exists in features[] (UNKNOWN_REF if missing)
   b. Self-edge — feature.id MUST NOT appear in its own depends_on or supersedes
      (SELF_EDGE if present)
   c. Acyclicity — build adjacency from depends_on across all features; DFS from
      each node; reject if any back-edge (CYCLE; include the offending edge)
6. Deprecation check (warn-only) — if feature.depends_on references a deprecated
   id, emit warning in response but do not block the write
7. Write file atomically (write to temp + rename in same directory)
   - On IO failure: return WRITE_FAILED; file untouched
8. Return { ok: true, persisted: <feature>, warnings?: [...] }
   or       { ok: false, error: <code>, detail: <message> }
```

Concurrency: atomic rename handles single-process safety. Two parallel MCP calls in the same session are not expected (Claude Code session is single-threaded); multi-session contention is out of scope for v5.0.

### Error surface

- `SCHEMA_VIOLATION` — JSONSchema validation failed; include path + message
- `UNIQUENESS_VIOLATION` — duplicate ids detected on file load
- `UNKNOWN_REF` — `depends_on`/`supersedes` references missing id
- `SELF_EDGE` — id appears in its own edge list
- `CYCLE` — DAG cycle detected; include the back-edge
- `WRITE_FAILED` — IO failure during atomic rename

No partial writes. On any error, file remains untouched.

## 3. Agent prompt deltas

### 3.1 `agents/product.md` — rewrite

Target shape:

- **Owns:** `<feature-id>-PRD.md`, `features.yaml` entry.
- **First turn ALWAYS** opens with `AskUserQuestion`:
  > "Does this requirement relate to any existing feature? If yes, which feature-id(s)?"
- Reads `features.yaml` and existing `docs/<feature-id>/*-PRD.md` before drafting.
- Manifest write via `mcp__orchestra-utils__upsert_features_yaml`.
- One PRD = one capability. Mixing guard per FR-7.
- Append-only graph (G6).
- Flags ADR-worthy decisions for `@architect` (stays from current @product).
- Tool surface: Read, Write, Edit, AskUserQuestion, Skill, `mcp__orchestra-utils__*`. No Bash. No `src/` write.

### 3.2 `agents/analyst.md` — new file

Frontmatter:

```yaml
---
name: analyst
description: "Authors FRS (BR + AC + pseudocode) from a locked PRD. Bridges business intent and technical pseudocode. Spawned by dispatcher after gate 2 approval."
tools: Read, Write, Edit, AskUserQuestion, Skill
model: claude-opus-4-7[1m]
---
```

(Verify model ID against `manifests/known-models.json` at implementation time.)

Body covers:

- Role: BR ↔ AC ↔ pseudocode translator.
- Input: `<feature-id>-PRD.md` (locked).
- Output: `<feature-id>-FRS.md` containing:
  - **BR** (business rules) — declarative statements the system MUST/MUST NOT do
  - **AC** (acceptance criteria) — observable test conditions
  - **Pseudocode** where it sharpens an AC
- FRS frontmatter MUST carry `subagent_session_id`, `phase`, `agent_role: analyst`, `artifact_id: <feature-id>-FRS` per `pipeline-artifact.schema.md` for observability joins via `metrics-collector.js`.
- No `src/` reads or writes. No Bash. No state mutation outside the FRS file.
- `AskUserQuestion` at ambiguity; frequency governed by `hooks/scripts/val-calibration.js` autonomy tier.
- Uses `skills/business-analysis/` for BR/AC discipline patterns.

### 3.3 `agents/architect.md` — expand scope

Target shape:

- **Owns:**
  - System-wide (only when `workspace_kind: multi-repo`): `SAD.md`, `ADR-NNNN.md`, `business-invariants.md`
  - Per-feature (always): `<feature-id>-TDD.md`, `<feature-id>-openapi.yaml` (or `<feature-id>-asyncapi.yaml` for async-only services)
- Inputs: PRD + FRS (+ SAD when system-wide).
- Brownfield: owns source-code exploration. Reads `src/**` to derive TDD + openapi during reverse-pass.
- C4: owns L1+L2+L3+L4.
- Tool surface: read `src/**`. No `src/` write.
- `AskUserQuestion` at ambiguity per val-calibration.

### 3.4 `agents/lead.md` — strip to orchestrator

Target shape:

- **Owns:** `TASKS`, `run-plan.md`. Nothing else.
- Input: TDD (business path) | intent (tech path).
- Action: invoke `skills/task-breakdown/` → emit run-plan → spawn parallel fan-out.
- Manages converge: `@test-runner` → `@evaluator` + `@reviewer`.
- Tech path: receives intent directly when zero design surface changes. If contract-touching work surfaces mid-task, halt and escalate to `@architect`.
- `AskUserQuestion` at ambiguity per val-calibration.

## 4. Dispatcher — `commands/orchestra.md`

Three concerns added: tech/business classification, manifest-aware feature-id assignment, 5-gate state machine.

### 4.1 Classifier prompt (inline in dispatcher)

```
You are classifying a user intent into one of two paths:

- "business": new user-visible feature, new endpoint, UI change, business rule change, data model change. Anything that changes what users can do or see.
- "tech": dependency bump, lint fix, internal refactor with zero contract change, observability tweak, build tooling, log format change. Anything with zero observable surface delta.

DEFAULT: business. When phrasing is ambiguous, choose business.

Confidence:
- HIGH — proceed silently to the chosen path.
- LOW or MEDIUM — call AskUserQuestion with the two options labelled "Business path" and "Tech path".
```

### 4.1.1 Feature-id assignment

Dispatcher (not `@product`) computes the next feature-id. Reads `.orchestra/<service>/features.yaml`, finds max numeric prefix across all `features[].id`, increments by 1, zero-pads to 3 digits. User supplies the slug at gate 1 (or as part of the original intent); dispatcher concatenates `<NNN>-<slug>`. Tech and business share the same counter (per FR-2).

Dispatcher passes the assigned id into `@product`'s spawn context. `@product` writes the manifest entry via MCP using that id; never invents its own.

### 4.2 Gate state machine

Each gate = one `AskUserQuestion` call from dispatcher (main thread), upstream agent returns first. Per `run-plan-gate-mode-split`: never inside a spawned agent.

```
                                  ┌──────────────────────────────────────────────┐
                                  │ Gate 1: tech | business confirmation         │
                                  │  fires only on LOW/MEDIUM classifier conf.   │
                                  └──────────────┬───────────────────────────────┘
                                                 │ approved
                          business path ◄────────┴────────► tech path
                                 │                                │
                                 ▼                                ▼
                          spawn @product                   spawn @lead (tech mode)
                                 │                                │
                          @product returns                        │
                          (PRD locked,                            │
                           manifest upserted)                     │
                                 │                                │
                                 ▼                                │
                          ┌─────────────────────────────────┐     │
                          │ Gate 2: PRD review → FRS?       │     │
                          └──────────────┬──────────────────┘     │
                                         │ approved               │
                                         ▼                        │
                                  spawn @analyst                  │
                                         │                        │
                                  @analyst returns                │
                                  (FRS locked)                    │
                                         │                        │
                                         ▼                        │
                          ┌─────────────────────────────────┐     │
                          │ Gate 3: FRS review → TDD?       │     │
                          └──────────────┬──────────────────┘     │
                                         │ approved               │
                                         ▼                        │
                                  spawn @architect                │
                                         │                        │
                                  @architect returns              │
                                  (TDD + openapi locked)          │
                                         │                        │
                                         ▼                        │
                          ┌─────────────────────────────────┐     │
                          │ Gate 4: TDD+openapi → impl?     │     │
                          └──────────────┬──────────────────┘     │
                                         │ approved               │
                                         ▼                        │
                          spawn @lead (business mode) ◄────────────┘
                                         │
                                  @lead returns
                                  (run-plan draft)
                                         │
                                         ▼
                          ┌─────────────────────────────────┐
                          │ Gate 5: run-plan approval       │
                          │  (existing forward-chain gate)  │
                          └──────────────┬──────────────────┘
                                         │ approved
                                         ▼
                                  parallel: @backend ‖ @frontend ‖ @test-author
                                         │
                                         ▼
                                  @test-runner → @evaluator + @reviewer
                                         │
                                         ▼
                                  TSR locked
```

### 4.3 Gate rejection paths

For each gate, user can choose:

- **Approve** → spawn downstream agent
- **Re-author** → unlock the upstream artifact (flip its frontmatter `status: locked` → `status: draft`), re-spawn the upstream agent with user feedback appended to spawn-context as a `Feedback:` block. The agent picks up its prior artifact in `draft` state and revises in place.
- **Halt** → stop chain; return summary; user resumes manually by re-invoking `/orchestra` (chain state recovers from filesystem — see §4.5).

Re-author is the most common non-approve. Halt is the escape hatch.

### 4.4 Chain state persistence

Dispatcher carries no state between user turns. On re-invocation, it derives current chain position from filesystem:

```
For the active <feature-id>:
  If <feature-id>-PRD.md absent             → run gate 1 → spawn @product
  If PRD present + status: locked, no FRS   → run gate 2 (or proceed if already approved)
  If FRS present + status: locked, no TDD   → run gate 3
  If TDD + openapi locked, no run-plan      → run gate 4
  If run-plan present + status: draft       → run gate 5
  If run-plan locked, implementation absent → spawn fan-out
  ...
```

`features.yaml` tells the dispatcher which `<feature-id>` is the "active" one (the one without a TSR verdict). No separate state file.

### 4.5 Brownfield reverse-pass

Reverses the chain: src → `@architect` → `@analyst` → `@product`. Gates in reverse:

```
reverse-pass plan-mode gate  (existing, EnterPlanMode/ExitPlanMode)
    │
    ▼
spawn @architect (brownfield mode, reads src/**)
    │
    ▼
Gate R-4: extracted TDD + openapi review
    │
    ▼
spawn @analyst (derives FRS from extracted TDD)
    │
    ▼
Gate R-3: derived FRS review
    │
    ▼
spawn @product (synthesizes PRD + manifest entry from FRS+TDD)
    │
    ▼
Gate R-2: synthesized PRD review → done
```

Reverse pass writes the manifest at the END (when `@product` synthesizes), not the start.
